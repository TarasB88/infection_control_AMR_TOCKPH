# AMR AST API — ручне введення та Excel

## Авторизація

У поточній версії API більше не використовує спільний Bearer `API_TOKEN` у браузері. Доступ до Worker захищається Cloudflare Access. Worker перевіряє підписаний JWT із заголовка `Cf-Access-Jwt-Assertion`, його issuer, строк дії та Application Audience (AUD), після чого зіставляє підтверджений email з профілем у D1.

Необхідні Production variables:
- `ACCESS_TEAM_DOMAIN` — домен команди Cloudflare Zero Trust.
- `ACCESS_AUD` — Application Audience tag захищеного Worker Access application.
- `INITIAL_ADMIN_EMAIL` — email першого адміністратора, який має бути дозволений політикою Access.

Необхідний секрет:
- `PATIENT_HMAC_SECRET` — незмінний секрет щонайменше 32 символи для HMAC-SHA-256 псевдонімізації Patient_ID.

**Не змінювати `PATIENT_HMAC_SECRET` після імпорту реальних даних.** Заміна секрету змінить псевдоніми пацієнтів. Старий `API_TOKEN` більше не використовується новою версією API; не видаляйте його з Production до підтвердження успішного переходу та розгортання нового входу.

Налаштування Access, міграції та створення адміністратора описані в [AUTHENTICATION_AND_USER_PROFILES.md](./AUTHENTICATION_AND_USER_PROFILES.md).

## Профілі та ролі

- `admin`: усі заклади, керування профілями, читання й запис.
- `operator`: ручне введення та Excel-імпорт лише для призначених кодів закладів.
- `analyst`: читання та експорт у межах призначених кодів закладів.

Дозвіл Cloudflare Access і профіль застосунку — два окремі рівні: email має бути допущений політикою Access, а також мати активний профіль у D1.

## AST поля

Один рядок — один результат AST для одного ізоляту та одного антимікробного препарату. Очікуються 16 колонок:

```text
Hospital_ID
Hospital_Name
Region_Oblast
Territorial_Hromada
Settlement
Patient_ID
Sample_ID
Sampling_Date
Sample_Matrix_Type
Bacterial_Species
Antimicrobial_Agent
MIC_Operator
MIC_Value
Zone_Diameter
SIR_Category
Interpretation_Standard
```

- `Hospital_ID` має збігатися з кодом закладу, призначеним профілю користувача.
- `Patient_ID` не зберігається у відкритому вигляді; Worker обчислює HMAC-SHA-256.
- `Sampling_Date` — `YYYY-MM-DD`.
- `MIC_Operator` — `=`, `<`, `>`, `<=`, `>=`, `≤` або `≥`.
- `MIC_Operator` зберігається окремо від `MIC_Value`.
- `SIR_Category` — окремі значення `S`, `I`, `R`.
- `Interpretation_Standard` має містити стандарт і версію, наприклад EUCAST 2026.

## Endpoints

### Поточна особа

```http
GET /api/auth/me
```

Повертає профіль поточного користувача та дозволені коди закладів.

### Адміністрування профілів

```http
GET /api/admin/users
POST /api/admin/users
Content-Type: application/json
```

Доступно лише активному адміністратору. POST створює або оновлює профіль за email; поля: `email`, `fullName`, `role`, `isActive`, `allFacilities`, `facilityCodes`.

### Читання AST

```http
GET /api/amr/ast?limit=500&offset=0
```

Повертає лише записи в межах прав доступу поточного профілю. Максимальний розмір сторінки — 1000.

### Excel імпорт

```http
POST /api/amr/ast/import
Content-Type: application/json
```

Тіло містить `sourceName` і масив `rows` до 1000 записів. UI читає Excel-файл у браузері, перевіряє наявність усіх 16 заголовків і передає рядки до Worker. Worker повторно перевіряє поля, роль і дозволені коди закладів, псевдонімізує Patient_ID і зберігає дані в D1.

### Ручне введення

```http
POST /api/amr/ast/manual
Content-Type: application/json
```

Використовує той самий payload і той самий валідатор, що й Excel-імпорт, але фіксує тип джерела `manual`.

## Коди відповідей

- `200`: читання або оновлення успішне.
- `201`: новий імпорт або профіль створено.
- `207`: частковий імпорт — частина рядків не пройшла валідацію.
- `400`: некоректний запит.
- `401`: користувач не пройшов Cloudflare Access.
- `403`: профіль не створений/деактивований, роль не дозволяє операцію або заклад не входить до призначеної області доступу.
- `413`: payload перевищує ліміт.
- `422`: жоден рядок не пройшов валідацію.
- `503`: не налаштовано Access, D1 або PATIENT_HMAC_SECRET.
- `500`: помилка запису/читання; перевірити Worker logs і D1.

## Ідентичність та повторний імпорт

Ідентичність ізоляту в поточному MVP визначається `Hospital_ID + Sample_ID + Bacterial_Species`; AST-запису — ізолятом, препаратом та стандартом інтерпретації. Ручне введення й Excel використовують спільний простір ідентичностей, щоб повторне внесення тієї самої сутності оновлювало запис, а не створювало дубль.

Якщо лабораторна форма має окремий стабільний `Isolate_ID`, модель потрібно буде розширити: `Sample_ID` сам по собі не гарантує однозначності, коли з одного зразка виділено кілька ізолятів того самого виду.

## Важливі обмеження

- Імпорт обмежений 1000 рядками і 5 МБ на запит.
- D1 batch-записи розбиваються на chunks; у разі помилки пізнішого chunk можливий частковий запис. Перед масовими імпортами потрібне тестування з резервною копією та звірка import_batches.
- Розрахунок відсотків резистентності не виконується цим endpoint. Потрібно окремо погодити знаменник, правила дедуплікації, період та версію EUCAST.
- Реальні дані не завантажувати до перевірки політик Access, резервного копіювання, журналу аудиту, правил зберігання і правових підстав обробки.
